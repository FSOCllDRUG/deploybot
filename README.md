# deploybot

Telegram-бот, который обновляет проекты на сервере без SSH. Подходит любому проекту, который собирается из git через `docker compose`.

- **📊 Состояние** — версия каждого проекта и сколько новых коммитов, контейнеры (работает или нет, CPU, память), память и диск сервера.
- **⬆️ Обновить** — показывает новые коммиты и после «Обновить» делает:
  1. `git pull --ff-only`;
  2. `docker compose up -d --build`;
  3. дополнительные команды для изменившихся файлов (`on_change`);
  4. через 20 секунд проверяет, что нужные сервисы работают.

  При ошибке присылает файл с полным выводом и логами. Без новых коммитов предлагает просто пересобрать (например, после правки `.env`).
- **📄 Логи** — `docker compose logs` (2000 строк каждого контейнера) файлом и число строк с ошибками.
- **🔄 Перезапуск** — `docker compose restart` выбранных сервисов и проверка, что они поднялись.
- **🐳 Docker** — все контейнеры сервера (и не из конфига тоже), по compose-проектам: 🟢 работает, ⚪ завершился без ошибки, 🟡 перезапускается, 🔴 упал. У каждого CPU и память, внизу сколько места занимает Docker и сколько можно освободить.
- **🖥 Сервер** — нагрузка процессора, память, swap и диск с полосками заполнения, время без перезагрузки, пять процессов, которые едят больше всего памяти.
- **⚙️ Вид** — «Красиво» (по умолчанию) или «Как в терминале»: буквальный вывод команд моноширинным блоком, с `$ команда` перед каждой — `git status -sb`, `docker compose ps`, `docker ps -a`, `docker stats --no-stream`, `docker system df`, `uptime`, `free -h`, `df -h /`, `ps`. Выбор у каждого чата свой и хранится в `/var/lib/deploybot/state.json`.

В красивом виде статусы Docker переведены на русский, длинные списки свёрнуты в цитаты, кнопки подтверждения цветные (Bot API 9.4; в старых клиентах просто без цвета). Слишком длинный ответ приходит файлом.

Один бот = один сервер. На сервере может быть несколько проектов: они обновляются независимо, при нескольких проектах бот спрашивает, какой. Бот обновляет и сам себя, если его папка указана в конфиге.

Только стандартная библиотека Python 3.8+, ставить ничего не нужно. Бот работает на хосте как systemd-сервис, а не в контейнере: так он сам вызывает `git` и `docker compose`.

## Безопасность

Кто управляет docker на сервере, тот управляет всем сервером. Поэтому:
- бот отвечает только id из `admins` и только в личном чате, остальных молча игнорирует;
- команды фиксированные, произвольный shell из Telegram не запускается;
- токен лежит в `/etc/deploybot/projects.ini` с правами `600`, в git не попадает.

Логи уходят в Telegram. Не пишите в логи проектов пароли и токены.

## Установка на новый сервер

1. **Бот.** В @BotFather `/newbot`, например `germany_deploy_bot`. У каждого сервера свой бот: Telegram не даёт двум серверам слушать один токен.
2. **Код** (от root):
   ```bash
   git clone https://github.com/FSOCllDRUG/deploybot /opt/deploybot
   cd /opt/deploybot && ./install.sh
   ```
   Если репозиторий закрытый, клонируйте его так же, как проекты, через deploy key.
3. **Конфиг.** Первый запуск `install.sh` создаёт `/etc/deploybot/projects.ini` из `projects.example.ini`. Впишите в него имя сервера, токен, свой Telegram id (его покажет @userinfobot) и проекты, затем снова:
   ```bash
   ./install.sh
   ```
4. Напишите боту `/start`: появятся кнопки.

Логи самого бота: `journalctl -u deploybot -f`.

## Новый проект

Проект должен лежать на сервере git-клоном с веткой, которая следит за удалённой (обычный `git clone` так и делает), и с `docker-compose.yml` в корне. В конфиг добавьте секцию:

```ini
[blog]
dir = /root/blog
check = web          # сервисы, которые обязаны работать после обновления
restart = web        # что перезапускает «Перезапуск»; пусто — весь проект
on_change =
    nginx.conf: restart nginx
```

Комментарии после `#` можно писать и в конце строки. Затем перезапустите бота: `systemctl restart deploybot`. Код менять не нужно. Какую ветку проекта обновлять, решает сама папка, см. «Ветки».

## Ветки

Бот обновляет ту ветку, на которой стоит папка проекта: `git pull` и список новых коммитов (`HEAD..@{u}`) берут ветку, за которой она следит. Посмотреть её можно в «📊 Состояние» в виде «Как в терминале», строка `git status -sb`, например `## main...origin/main`. Ветка нигде в конфиге не указывается.

### Сменить ветку проекта (например, `mvp` → `main`)

1. **Ветка должна быть на GitHub.** Если её нет, создайте её на своём компьютере из текущей:
   ```bash
   git push origin mvp:main
   ```
   По желанию сделайте её веткой по умолчанию (на неё смотрят `git clone` и PR):
   ```bash
   gh repo edit <владелец>/<репозиторий> --default-branch main
   ```
2. **Переключите папку на сервере** (один раз, по SSH):
   ```bash
   cd /root/zapasik && git fetch && git switch main
   ```
   `git switch` сам создаст локальную `main`, которая следит за `origin/main`. Файлы, которых нет в git (`.env`, `docker-compose.override.yml`), не трогаются.
   - Git отказался из-за локальных изменений? Посмотрите `git status`: правки на сервере обычно лишние, `git restore .` их убирает.
   - Локальная `main` уже была, но без связи с GitHub (`git status -sb` не показывает `...origin/main`)? Свяжите её: `git branch -u origin/main`.
3. **Пересоберите, если код в ветках разный.** `git switch` уже поменял файлы, но контейнеры ещё работают на старом коде. Нажмите «⬆️ Обновить»: новых коммитов не будет, бот предложит «Пересобрать». Если обе ветки указывают на один коммит, ничего делать не нужно.
4. **Проверьте** в «📊 Состояние» (вид «Как в терминале»): `## main...origin/main` и нужный коммит. Дальше пушьте в `main`, бот будет предлагать её коммиты.

Конфиг бота менять не нужно. Старую ветку на GitHub можно удалить (`git push origin --delete mvp`), серверу она больше не нужна.

### Две ветки одного репозитория (prod и staging)

Каждая ветка — отдельная папка-клон и отдельная секция в конфиге:

```bash
git clone -b staging git@github-zapasik:FSOCllDRUG/zapasik.git /root/zapasik-staging
```

```ini
[zapasik]
dir = /root/zapasik            # main
check = app

[zapasik-staging]
dir = /root/zapasik-staging    # staging
check = app
```

Они обновляются независимо, у каждой секции своя блокировка. Чтобы копии не мешали друг другу:
- **Имя compose-проекта.** По умолчанию это имя папки, поэтому у каждой копии свои контейнеры и тома (база не общая). Если в `docker-compose.yml` задан верхнеуровневый `name:`, обе копии получат одно имя и начнут заменять контейнеры друг друга. Тогда пропишите каждой папке своё имя в её `.env`: `COMPOSE_PROJECT_NAME=zapasik-staging`.
- **Порты.** Порты 80 и 443 может занять только одна копия. Вторую запускайте без своего прокси, а основной прокси (Caddy или nginx) пусть ведёт на неё отдельный домен, например `staging.example.com`. Изменения для копии держите в `docker-compose.override.yml` в её папке: compose подхватывает этот файл сам, а `git pull` его не трогает, если он не в git.
- **`.env` у каждой папки свой:** свои адреса, пароли и токены. Токен Telegram-бота должен быть **другим**: один токен нельзя слушать из двух мест сразу.
- **Память.** Каждая копия — ещё один набор контейнеров. Проверьте запас в «🖥 Сервер».

Переключать одну папку между ветками туда-сюда не стоит: легко забыть, какая ветка сейчас на проде. Отдельная папка на ветку проще и надёжнее.
